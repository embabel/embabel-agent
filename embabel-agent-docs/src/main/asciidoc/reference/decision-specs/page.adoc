[[reference.decision-specs]]
=== Decision specs (experimental)

A decision spec is an ordered set of named questions that a model answers in one decision.
A decision response holds the model's answer to each question.
The types are in `embabel-agent-ai`, in the package `com.embabel.common.ai.decision`.
The JSON bindings are in the package `com.embabel.common.ai.decision.json`.

This page covers building, serializing and reading specs and responses.
It does not cover running a spec against a decision service.

Every type on this page carries `@ApiStatus.Experimental`.
The types become stable once they have a named owner, a consumer application that uses them, and a compatibility assessment.
Promotion is decided at the first release after all three are in place.

==== Types

|===
|Type |Holds

|`DecisionRequest`
|The input text and one `DecisionSpec`

|`DecisionSpec`
|An ordered list of `Question` values with unique names, and an `s1-` definition id

|`Question`
|A kind, a name, instructions, the options or levels for its kind, and a `d1-` definition id

|`DecisionResponse`
|The spec's `s1-` id, the execution mode, an optional request failure, and one `DecisionAnswer` per question in spec order

|`DecisionAnswer`
|The question's name, kind and `d1-` id, its options or levels, and a typed outcome
|===

A response holds no question objects, no instructions and no input.
Code can read a response without the spec that produced it.

==== Builder

[source,java]
----
include::../../../../../../embabel-agent-common/embabel-agent-ai/src/test/java/com/embabel/common/ai/decision/DecisionSpecJavaTest.java[tag=builder,indent=0]
----

`DecisionSpec.builder()` starts an empty builder.
The `proposition`, `choice` and `rating` methods each take a question name and a customizer.
The customizer receives a builder of that kind that already carries the name.
It runs once, before the method returns.

A blank or repeated name throws `IllegalArgumentException`, and the customizer does not run.
An invalid definition also throws `IllegalArgumentException`.
A declaration that throws adds nothing to the builder.
A customizer that declares a question on its own enclosing builder gets an `IllegalStateException`.

`build()` returns a new spec on each call.
Later declarations do not change specs already built.
`build()` throws `IllegalArgumentException` when no question has been declared.
A builder is not safe for use from several threads at once.

A spec is immutable.
`getQuestions()` returns the questions in declared order.
`question(name)` returns the question with that name, or `null` when there is none.
Two specs are equal when they hold equal questions in the same order.

`Questions.named(name)` starts a question on its own.
Its `proposition`, `choice` and `rating` methods take the instructions and return the builder for that kind.
A question built this way can live in a field, join several specs, and read its typed answer from a response.

`DecisionSpec.of` takes questions as arguments or as a list.
`DecisionSpec.Builder.question(question)` adds a question built earlier to a builder.
The spec in this example equals a spec built with the builder from the same two questions.

==== Kotlin DSL

[source,kotlin]
----

`decisionSpec { }` builds a spec from a receiver block on `DecisionSpecScope`.
The block runs once.
Each call inside it goes through the matching `DecisionSpec.Builder` method, so a DSL spec validates exactly like a builder spec.
`DecisionSpecScope.question(question)` adds a question built earlier.
The spec is built once, after the block returns.

The `@DecisionSpecDsl` marker sits on the scope and on the three question builders.
Code inside a question block cannot call the enclosing spec scope without an explicit label.
Java code does not see `decisionSpec` or the scope methods.

==== Question kinds

|===
|`QuestionKind` |Question class |Builder methods |Result type |Wire name

|`PROPOSITION`
|`PropositionQuestionSpec`
|`asking`
|`PropositionResult`
|`proposition`

|`CHOICE`
|`ChoiceQuestionSpec`
|`asking` and `option(id, description)`, with at least one option
|`ClassificationResult`
|`choice`

|`RATING`
|`RatingQuestionSpec`
|`asking`, `level(label)` and `level(id, description)`, with at least two levels added lowest first
|`RatingResult`
|`rating`
|===

Every question needs a nonblank name and nonblank instructions.
Option ids and level ids must be nonblank and unique within their question.
`level(label)` uses the label as the level's id and description.
Choice options are `Category` values.
Rating levels are `RatingLevel` values, and the first level has index 0.

`ChoiceQuestionSpec.validate(result)` and `RatingQuestionSpec.validate(result)` check that a result fits the question.
Each returns the result unchanged or throws `IllegalArgumentException`.

==== Rating evidence

`RatingResult` has three classes: `Answered`, `Inconclusive` and `Failure`.
`Inconclusive` holds a `ModelProvenance`.
`Failure` holds a `FailureReason`.
`Answered` holds the evidence in this table:

|===
|Property |Type |Rule

|`provenance`
|`ModelProvenance`
|Required

|`selectedLevelId`
|`String`, optional
|Nonblank. It must be one of the question's level ids.

|`distribution`
|`List<LevelProbability>`
|Empty, or it covers exactly the question's levels in any order. Each probability is finite and between 0 and 1. The probabilities sum to 1 within `1e-6`.

|`score`
|`RatingScore`, optional
|The value is finite, at least 0, and at most the index of the last level.

|`confidence`
|`Double`, optional
|Finite and between 0 and 1
|===

An `Answered` result reports a selected level, a distribution, a score, or a combination of these.
It holds only what the provider reported.
It never carries a selected level derived from a score, and it never invents a distribution.

A `RatingScore` pairs a value with a `RatingStatistic`.
The one statistic is `EXPECTED_LEVEL_INDEX`, the probability-weighted mean of the zero-based level positions.
It is a continuous number over the level range.

The checks against the question's levels run when a result is validated against a `RatingQuestionSpec` or added to a response.
The other rules run when the result is constructed.

==== Definition ids

Each question has a `definitionId` that starts with `d1-`.
Each spec has a `definitionId` that starts with `s1-`.
A question's id changes when its kind, name, instructions, or any option or level changes, including their order.
Equal question definitions have equal ids.
A spec's id changes when any question changes, or when questions are added, removed or reordered.

Code that writes decision JSON outside this library computes the same ids with this recipe.
An id is a prefix followed by the SHA-256 digest of a canonical JSON text.
The digest is encoded as unpadded base64url, as in RFC 4648 section 5.
Every id is the prefix plus 43 characters.

|===
|Id |Prefix |Canonical text

|Question
|`d1-`
|The JSON array `[kind, name, instructions, [[id, description], ...]]`

|Spec
|`s1-`
|The JSON array of the spec's question ids, as strings, in question order
|===

The kind is the lower-case wire name from the question kinds table.
The last element of a question's array lists the options or levels as `[id, description]` pairs in declared order.
For a proposition it is `[]`.

The canonical text is compact JSON, written by these rules:

|===
|Content |Written as

|Space between tokens
|None

|String content
|As given, with no trimming and no Unicode normalization

|`"` and `\`
|`+\"+` and `+\\+`

|Backspace, tab, line feed, form feed and carriage return
|`+\b+`, `+\t+`, `+\n+`, `+\f+` and `+\r+`

|Every other character below U+0020
|A backslash, the letter `u` and four hex digits with upper-case letters, so U+001F becomes `+\u001F+`

|An unpaired surrogate
|The same escape, so U+D800 becomes `+\uD800+`

|Everything else, including `/`, U+007F, U+2028 and all non-ASCII text
|Unescaped
|===

The text is encoded as UTF-8, with each supplementary character written as one four-byte sequence.
The digest is taken over those bytes.

A proposition named `is_urgent` that asks `The customer needs a reply today.` has this canonical text:

[source,json]
----
["proposition","is_urgent","The customer needs a reply today.",[]]
----

Its id is `d1-81hzfR8Ooim5eJZok_AQMmXVY5l_p2bImz3be95T9z8`.
The number after the prefix letter is the algorithm version.
A change to the recipe gets a new prefix.

==== Responses

`DecisionResponse.builder(spec, executionMode)` starts a response to a spec.
Its `answer(question, outcome)` overloads take a question of each kind with the matching result type.
Answers can be added in any order, and the response lists them in spec order.
`DecisionResponse.failed(spec, executionMode, reason)` records a request that failed as a whole.
Every answer in a failed response is a failure with that reason, and `getRequestFailure()` returns it.

The builder's `answer` method throws `IllegalArgumentException` in these cases:

* The spec has no question with that name.
* The spec's question has a different definition id.
* The question already has an answer.
* A choice selection is not one of the options.
* Rating evidence does not fit the levels.

`build()` throws `IllegalArgumentException` when a question of the spec has no answer.
A response always checks that its answers' definition ids give its `s1-` id.
That check catches a dropped, extra or reordered answer.

`answer(name)` returns the `DecisionAnswer` with that name.
It throws `IllegalArgumentException` when the response has no answer with that name.
`DecisionAnswer` is sealed, with the classes `DecisionAnswer.Proposition`, `DecisionAnswer.Choice` and `DecisionAnswer.Rating`.
A Java `switch` or a Kotlin `when` over an answer covers every case.
`DecisionAnswer.Choice` also holds the question's options, and `DecisionAnswer.Rating` holds its levels.

==== Requests and options

`DecisionRequest.of(input, spec)` pairs an input with a spec.
`DecisionRequest.of(input, questions...)` builds the spec from the questions in order.
The input may be empty.
A request's `toString()` shows the spec and leaves the input out.

`ExecutionMode` names the ways a spec can run:

|===
|Mode |Meaning

|`NATIVE`
|The whole spec is evaluated in one provider operation, so every answer shares one model evaluation.

|`SINGLE_QUESTION`
|A spec with one proposition or choice question is answered through the matching existing service method. A single rating question has no such method.

|`SEQUENTIAL`
|Each question is asked in its own call.
|===

`DecisionOptions` holds the modes a caller allows.
Its `executionModes` set holds at least one mode and iterates in enum declaration order.

|===
|Factory |Allowed modes

|`DecisionOptions.defaults()`
|`NATIVE` and `SINGLE_QUESTION`

|`DecisionOptions.nativeOnly()`
|`NATIVE`

|`DecisionOptions.allowingSequential()`
|All three

|`DecisionOptions.of(executionModes)` and `DecisionOptions.of(first, rest...)`
|Exactly the given modes
|===

`DecisionCapabilities` describes what a service accepts.
`DecisionCapabilities.of(questionKinds, executionModes)` sets the supported kinds and modes.
`withMaxQuestions` and `withMaxInputCharacters` each return a copy with that limit set.
A `null` limit means the service does not report that limit.

==== JSON format

Each decision type has fixed member names:

|===
|Type |Members

|`Question`
|`kind`, `name`, `instructions`, then `options` for a choice or `levels` for a rating

|`DecisionSpec`
|`questions`

|`DecisionRequest`
|`input` and `spec`

|`DecisionOptions`
|`executionModes`

|`DecisionCapabilities`
|`questionKinds`, `executionModes`, and the optional `maxQuestions` and `maxInputCharacters`

|`DecisionResponse`
|`definitionId`, `executionMode`, the optional `requestFailure`, and `answers`

|`DecisionAnswer`
|`kind`, `definitionId`, `options` or `levels` for its kind, and `outcome`

|Option or level
|`id` and `description`
|===

The `answers` member is an object that maps each question name to its answer, in spec order.
An answer inside a response takes its name from its key.
An answer written on its own also has a `name` member after `kind`.
Execution modes, failure reasons and rating statistics use the lower-case constant name, such as `single_question`, `invalid_response` and `expected_level_index`.
Question kinds use the wire names from the question kinds table.

Each outcome has a `status` member that names its result class:

|===
|Kind |`status` |Other members

|Proposition
|`answered`
|`answer` and `provenance`, and the optional `pTrue`

|Proposition, choice and rating
|`inconclusive`
|`provenance`

|Proposition, choice and rating
|`failure`
|`reason`

|Choice
|`selected`
|`categoryId` and `provenance`, and the optional `confidence`

|Choice
|`no_match`
|`provenance`

|Rating
|`answered`
|`provenance`, and the optional `selectedLevelId`, `distribution`, `score` and `confidence`
|===

A `provenance` object has `modelName` and `provider`, and the optional `version` and `requestId`.
A `distribution` entry has `levelId` and `probability`.
A `score` has `value` and `statistic`.
An explicit `null` in an optional member reads the same as an absent member.

`DecisionJacksonModule` reads and writes `Question` and its three classes, `DecisionSpec`, `DecisionRequest`, `DecisionOptions`, `DecisionCapabilities`, `DecisionResponse`, `DecisionAnswer` and its three classes, and `RatingResult` and its three classes.
It registers no binding for any other type.
`PropositionResult`, `ClassificationResult` and `ModelProvenance` keep their existing JSON everywhere outside a decision response.
Writers use the fixed member names in a fixed order and ignore the mapper's naming strategy.

The module is listed for Java's `ServiceLoader`, so `JsonMapper.builder().findAndAddModules()` adds it.
Spring Boot's Jackson auto-configuration finds modules the same way.
A Spring Boot application's auto-configured mapper reads and writes decision types with no bean or other setup.
The platform's own mapper from `EmbabelObjectMapperHolder.createDefault()` also adds the module.

==== Strict parsing

Every decision deserializer fails with `MismatchedInputException` on input the types do not allow:

|===
|Input |Message

|A repeated member
|`Duplicate member '<name>' in <Type>`

|An unknown member
|`Unknown member '<name>' in <Type>`

|A missing required member
|`Missing required member '<name>' in <Type>`

|A value of the wrong JSON type, or an unknown kind, mode, status, reason or statistic
|`Member '<name>' in <Type> must be <expected>`

|A value a builder or factory refuses
|The builder's message, with the `IllegalArgumentException` as the cause
|===

`<Type>` is the simple class name of the type being read.
These checks run on the token stream, so they hold whatever the mapper's duplicate and unknown-property settings are.
A kind or mode that appears twice in one array also fails.
A member that a later version adds fails in a reader that does not know it.
A response whose answers are out of spec order fails the `s1-` id check.

===== Parsed trees

`readTree` keeps only the last value of a repeated member.
A decision type read from that tree with `treeToValue` cannot detect the duplicate.
Every other check still runs on a tree.
Read decision JSON with `readValue` from text, bytes or a stream to detect duplicate members.

==== Projection

`DecisionProjection.of(response, type)` reads the response's answered values and converts them to a caller type with Jackson.
The result holds the converted `value` and the original `response`.
`DecisionProjection.answeredValues(response)` returns the values as a map keyed by question name:

|===
|Answer |Value

|Proposition
|The `answer` of a `PropositionResult.Answered`

|Choice
|The `categoryId` of a `ClassificationResult.Selected`

|Rating
|The `selectedLevelId` of a `RatingResult.Answered`
|===

Any other outcome has no value, and neither does a rating answered with only a score or a distribution.
Both calls then throw `DecisionProjectionException`, and its `getQuestions()` lists every answer without a value.

A record whose component names match the question names receives the values.
The `type` argument is a `Class<T>` or a `TypeReference<T>`, and a `TypeReference<T>` suits a generic target such as a map.
Each overload also takes an optional `ObjectMapper`.
The default mapper fails when a constructor parameter of the target has no answered value.
A mapper passed in keeps its own settings.
A failed conversion throws `DecisionProjectionException` with an empty `getQuestions()` and the Jackson exception as the cause.
