=== Decision model providers

A `DecisionService` can be answered by a decision model like Jev, by a chat model prompted to decide, or by your own code.
Decision models are configured the same way chat models are.
Put a provider starter on the classpath and it registers one `DecisionService` bean per model in its catalog, named after the model.
Defaults and roles pick a model by name.

|===
|Source |How a model becomes available |Example name

|Catalog starter
|The starter loads `models/<provider>-models.yml` and defines a bean per entry. Inject one by type or with `@Qualifier("<model>")`.
|`jev-latest`, `clef`

|`DecisionModelProvider` bean
|The registry asks the provider the first time a default, role or `named` lookup uses a name no bean holds
|A chat model name, such as `gpt-4.1-mini`

|Application bean
|A singleton `DecisionService` or `ClassificationService` bean registers under its bean name. A `@Lazy` or scoped bean is left out.
|`triage`

|Provider function
|`DecisionService.from(metadata, capabilities, executor)` makes a service from one function. Define the service as an application bean to register it.
|`refund-rules`
|===

==== Provider models

`DecisionModelProvider` supplies services by name for models that are not beans.
`LlmDecisionServiceFactory` is the provider for chat models.
It serves every chat model the `ModelProvider` lists and builds a prompted decision service for the one you name.

|===
|Member |Contract

|`provider`
|Provider name. Registry error messages list each provider's models under it.

|`modelNames()`
|Names the provider can serve now. The registry checks a default or role against this list only when no bean holds the name.

|`decisionServiceNamed(name)`
|The service for a name, or null when the provider does not serve it
|===

The registry asks providers in order and keeps the first service returned, so each name is built once.
A registered bean wins over a provider model with the same name.
A provider model is a family default only when configuration names it.
A provider builds services that use the deployment's own credentials. Per-user keys go through `using(service)`.

==== Writing a provider

`DecisionExecutor` is the one function a provider writes.
It receives a `DecisionCall` and returns a `DecisionResponse` with one answer per question.
`DecisionService.from(metadata, capabilities, executor)` makes a `DecisionService` from it.
`DecisionService.KIND` is the model kind for decision services.

This provider answers one proposition or one choice question from text with fixed rules.
Its capabilities allow one question per call.

Every way of asking the service reaches the executor as one call, including `assess` and `classify`.
The call is checked against the capabilities before the executor runs.
The checks run in this order:

|===
|Check |The call is rejected when

|Question kinds
|A question's kind is not in `questionKinds`

|Question count
|The spec holds more questions than `maxQuestions`

|Arity
|A choice question's option count or a rating question's level count is outside the arity stated for its kind

|Input
|The input is neither text nor a kind in `nativeInputKinds`, or the call requires native JSON and `nativeInputKinds` leaves out `json`

|Option keys
|The call sets an option whose id is not in `supportedCallOptionIds`

|Preflight
|The provider's preflight check throws
|===

A failed capability check throws `UnsupportedDecisionException` and the executor is not called.
A spec that exceeds `maxQuestions` is rejected whole.
The framework never splits it into smaller calls.
A preflight exception reaches the caller unchanged.
When `nativeInputKinds` leaves out `json`, a JSON input reaches the executor as its compact text.
A response that does not answer the call's spec becomes an `INVALID_RESPONSE` failure for every question.
An exception the executor throws reaches the caller unchanged.

`DecisionService.builder(metadata, capabilities, executor)` adds default options and a preflight check from Java.
In Kotlin, `DecisionService(metadata, capabilities, executor)` takes a block with the same settings.

|===
|Setting |Java builder |Kotlin block |Effect

|Default option
|`withDefaultOption(key, value)`
|`defaultOption(key, value)`
|Fills in an option the call leaves unset. The capabilities must list the option.

|Preflight
|`withPreflight(check)`
|`preflight(check)`
|Runs on the call the executor would get, after the capability checks. Throwing stops the ask.
|===

Defaults are filled in before the option keys are checked.
When the call has a `DecisionOptions.TIMEOUT`, the executor gets a call whose timeout is the time left since the ask began.
With no time left, every question fails as `UNAVAILABLE` and the executor is not called.

==== Calls and options

`DecisionCall` holds the input, the spec and the options for one call.
`ask(call)` sends it to a service.
The input is a `TextDecisionInput` or a `JsonDecisionInput`.
`requiringNativeJson()` asks for a JSON input to reach the model as JSON.
It throws `IllegalArgumentException` for any other input.
A `DecisionOption<T>` is a typed key with a namespaced id, such as `openai.prompt-cache-key`.

How a service treats a call depends on how it was made:

|===
|Service |Call options |Native JSON required |JSON input

|Made with `DecisionService.from`
|Checked against `supportedCallOptionIds`
|Needs `json` in `nativeInputKinds`
|Sent as JSON when `nativeInputKinds` lists `json`, and as text otherwise

|Any other `DecisionService`
|Rejected
|Rejected
|Sent as text
|===

An option the service does not support is rejected before the provider is called.
No option is dropped silently.
Option values stay out of request JSON, logs and observations.
`DecisionCall.toString()` shows the input kind, question names and option ids.
It leaves out option values and the input.
A `DecisionCall` has no JSON form.
Use a `DecisionRequest` for a document you store or send.
`ObservedDecisionService` records one `embabel.ai.ask` and one `embabel.ai.decision` observation for an ask of a service made with `DecisionService.from`.
The `embabel.ai.decision` observation has the operation `ask_question_set`.
Observations read only the spec.

`OpenAiDecisionOptions` in `com.embabel.agent.openai.decision` publishes the OpenAI option keys:

|===
|Key |Id |Kotlin property |OpenAI limit

|`PROMPT_CACHE_KEY`
|`openai.prompt-cache-key`
|`promptCacheKey`
|64 characters

|`SAFETY_IDENTIFIER`
|`openai.safety-identifier`
|`safetyIdentifier`
|128 characters
|===

In Kotlin, the `openAi` block inside a `DecisionCall` block sets the keys by name.
The block does not check the length limits.
The keys are published before the OpenAI decision adapter.
This release does not include that adapter.

==== Declaring capabilities

`DecisionCapabilities` states what a service accepts.
Only the question kinds are required.
A declaration left out means the service does not say.

|===
|Declaration |Java chain |Kotlin block |When left out

|Question kinds
|`DecisionCapabilities.of(kinds)`
|`DecisionCapabilities(kinds) { }`
|Required

|Native inputs
|`acceptingInput(kind)`
|`input(kind)`
|Text only. A JSON input is sent as text.

|Question limit
|`withMaxQuestions(max)`
|`maxQuestions = max`
|No limit

|Call options
|`acceptingOption(key)`
|`option(key)`
|No option is accepted

|Arity
|`withArity(kind, min, max)`
|`arity(kind, min, max)`
|Any option or level count

|Evidence
|`reporting(kind, evidence...)`
|`reports(kind, evidence...)`
|Not stated

|Confidence measure
|`withConfidenceMeasure(kind, measure)`
|`confidence(kind, measure)`
|Not stated
|===

Each chain method returns a new value.
A per-kind declaration for a kind outside the question kinds throws `IllegalArgumentException`.
Evidence and confidence measures describe answers.
They are not checked against calls.
`confidenceMeasure(kind)` returns a `ConfidenceMeasure`, which says what a provider's confidence number measures.
Two providers can report the same confidence and mean different things.

|===
|Evidence kind |What the service reports

|`TRUE_PROBABILITY`
|A probability that a proposition is true

|`CATEGORY_DISTRIBUTION`
|A probability for each option of a choice question

|`LEVEL_DISTRIBUTION`
|A probability for each level of a rating question

|`EXPECTED_LEVEL_INDEX`
|The expected position on a rating scale, as a fractional level index

|`CONFIDENCE`
|A confidence figure, whose meaning the confidence measure states

|`REFUSAL`
|An explicit refusal to answer a question
|===

==== Refusals and usage

A provider reports a refused question with `DecisionResponseAssembler.refused(name, provenance)`.
A refused question has the `Inconclusive` outcome of its kind.
`DecisionResponse.wasRefused(question)` tells a refusal from an inconclusive answer.
`DecisionResponse.refusedQuestions` lists the refused question names in spec order.
A failed request lists no refusals.

A provider reports token counts with `DecisionResponseAssembler.usage(usage)`.
The usage is attached to the response, including a failed one.
`DecisionResponse.usage` is null when the provider reported nothing.

|===
|`DecisionUsage` count |Tokens counted

|`inputTokens`
|Read from the request

|`outputTokens`
|Written in the reply

|`totalTokens`
|The provider's own total

|`cacheReadInputTokens`
|Input served from the provider's cache

|`cacheWriteInputTokens`
|Input written to the provider's cache

|`reasoningTokens`
|Spent on hidden reasoning
|===

Each count is optional.
A missing count means the provider did not report it.

==== Credentials

A catalog starter reads its key the same way the chat model starters do, from the environment variable first and then the `api-key` property.
TypeSafe uses `TYPESAFE_API_KEY` and `embabel.agent.platform.models.typesafe.api-key`; `TypeSafeModelsConfig` requires one at startup even when application beans replace every catalog model service.
A custom `TypeSafeModelFactory` is a separate path: providing one makes the TypeSafe starter configuration back off, so the starter key check does not run.
Cloudflare uses `CLOUDFLARE_API_TOKEN` and `embabel.agent.platform.models.cloudflare.api-key`, plus an account id, and startup fails without them.
For a key supplied at run time, `TypeSafeModelFactory`, `CloudflareModelFactory` and every other `SystemOneModelFactory` implement `ByokFactory<DecisionService>`.
`buildValidated()` checks the key with the provider and returns a service, which you pass to `using(service)`.
See <<reference.typesafe>>, <<reference.cloudflare>> and <<reference.systemone>>.
