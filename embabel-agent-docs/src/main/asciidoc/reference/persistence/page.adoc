=== Persistence

Agent process persistence is a checkpointing mechanism for recovering processes
that are parked for external input, and for advancing durable state at terminal
lifecycle boundaries.

The framework keeps storage backend-neutral. Applications provide an
`AgentProcessSnapshotStore`; framework support creates snapshots, serializes
them, restores process instances, and decorates an
`InMemoryAgentProcessRepository` or another runtime `AgentProcessRepository`.

==== Lifecycle Boundaries

The initial persistence model supports two checkpoint boundaries:

* `WAITING`: a process has called `waitFor` and can be restored by another
  runtime after local process state is lost.
* Finished states: a process has completed, failed, been killed, or been
  terminated, and durable state should reflect that final lifecycle state.

`WaitForCheckpointPolicy` checkpoints only `WAITING` processes. Use it when the
snapshot store is only a recovery cache.

`LifecycleCheckpointPolicy` checkpoints `WAITING` and finished processes. Use it
when the durable snapshot should also show that the resumed process reached a
terminal state.

==== Storage

`AgentProcessSnapshotStore` is the storage SPI. It stores serialized snapshots
with process id, parent id, agent name, status, content type, payload, timestamps,
and optimistic version metadata.

The framework does not ship a JDBC, cache, Redis, or database implementation in
the agent API. Those backends should live in applications, starters, or tests.
The API test suite includes an H2/JDBC fixture to prove the end-to-end recovery
pattern without making JDBC part of the framework.

==== Configuration

Persistence activates when the application context contains an
`AgentProcessSnapshotStore` bean. Adding a store is enough; no other
configuration is required. Without one, the platform uses
`InMemoryAgentProcessRepository` exactly as before.

[source,properties]
----
# Turn persistence off without removing the snapshot store. Default true.
embabel.agent.platform.persistence.enabled=true

# WAITING or LIFECYCLE. Default LIFECYCLE.
embabel.agent.platform.persistence.checkpoint-policy=LIFECYCLE
----

`BlackboardEntrySerializer` beans are discovered automatically and consulted in
Spring `@Order` before the JSON fallback.

Applications that assemble the platform themselves, rather than through Spring
configuration, can build the same repository directly:

[source,kotlin]
----
val repository = AgentProcessPersistence.persistentRepository(
    runtimeRepository = InMemoryAgentProcessRepository(),
    snapshotStore = mySnapshotStore,
    objectMapper = objectMapper,
    agents = agentPlatform::agents,
    platformServices = { agentPlatform.platformServices },
)
----

The snapshot, serialization and restore machinery stays internal, so the
snapshot format remains free to change. The contracts an integrator implements,
`AgentProcessSnapshotStore`, `AgentProcessCheckpointPolicy` and
`BlackboardEntrySerializer`, are the stable surface.

==== Blackboard Values

Blackboard state is persisted through `BlackboardEntrySerializer`.
Serializers use `supportsSerialization` for live blackboard values and
`supportsDeserialization` for stored values.

The default JSON serializer is useful for simple values that can be safely
materialized. Applications should provide more specific serializers for values
that need stable identity or special treatment, such as:

* awaitables whose ids must survive restore;
* JPA/Hibernate entities that should be stored as references;
* sensitive values that should be encrypted or redacted;
* runtime handles that must be replaced by a durable DTO.

Custom serializers are resolved before the fallback serializer.

==== Current Limitations

The current snapshot factory supports `InMemoryBlackboard` and assumes a
`WAITING` process has exactly one pending awaitable. Broader blackboard support
should be added through a `BlackboardSnapshotter` SPI.

Runtime repository writes and snapshot writes are separate operations. The
expected-version check prevents stale snapshot updates, but rejected checkpoints
currently propagate to the caller. Transaction-backed runtime and snapshot
semantics require a persistent `AgentProcessRepository` using the same
transaction boundary as the snapshot store.

Snapshots use the process implementation JVM class name as an internal restore
discriminator. Moving or renaming process implementation classes requires
snapshot migration support.

==== Restore

On lookup, `PersistentAgentProcessRepository` first checks the runtime
repository. In the current tests this is an `InMemoryAgentProcessRepository`.
If the in-memory process is missing, it loads the serialized snapshot, rebuilds
the blackboard, reconstructs the process implementation, restores internal
status and action history, then saves the restored process back into the
in-memory repository.

This allows a HITL flow to resume after pod-local memory has been lost:

[source,text]
----
POST /start
  -> process WAITING
  -> snapshot version 1 stored
  -> runtime process lost
POST /continue
  -> snapshot loaded
  -> awaitable restored
  -> process resumes
  -> terminal snapshot version 2 stored
----
